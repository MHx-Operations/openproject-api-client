<objective>
Fix BUG-02: resource-class href parsing crashes with `ValueError` on `None`, empty strings, and URN-style hrefs (e.g. `urn:openproject-org:api:v3:undisclosed`). Only `Project.parent_id` currently guards against URNs (line 114). Every other resource (WorkPackage, Relation, Membership, Status, Grid, Query, TimeEntry, Activity, Attachment, Notification, Category) silently uses raw `int(href.split('/')[-1])` — a known crash for work packages whose parent is undisclosed (28 direct `int(...split...[-1])` sites + 2 compound `parts = href.split("/"); int(parts[-1])` sites at Attachment.container_id (line 768) and Notification.resource_id (line 806) = **30 sites total** that route through `_parse_href_id`).

Additionally, there are **5 sites** that extract the type segment via `[-2]` (WorkPackage.author_type / assignee_type / responsible_type at lines 227/233/239, plus Membership.principal_type at line 460 and the compound `parts[-2]` reads at Attachment.container_type line 769 and Notification.resource_type line 807). These do NOT route through the helper (they want the resource-type slug, not an int) but they MUST be guarded against URN/empty/None hrefs in the same way.

Centralize the int parse into one helper, `_parse_href_id(href) -> Optional[int]`, that returns `None` for any unparseable input. Replace every inline call site to use it. Add direct unit tests for the helper plus integration tests for the highest-risk resource classes.

Purpose: Eliminate the cluster of `ValueError` crashes documented in CONCERNS.md "Known Bugs" and "Fragile Areas".
Output: One helper function, 30 id-parse call site replacements, 5 type-segment URN guards, new tests.
</objective>

def _parse_href_id(href) -> int | None:
    """Return the trailing integer ID from an OpenProject _links href, or None.

    Returns None for: None, empty string, URN-style hrefs
    (e.g. 'urn:openproject-org:api:v3:undisclosed'), and any href whose
    final path segment is not a base-10 integer.
    """

NOTE on Python 3.9 syntax: `int | None` as a runtime annotation requires Python 3.10+. With `from __future__ import annotations` (present at the top of resources.py), the annotation is a string and is NOT evaluated at runtime — so `int | None` is safe on 3.9. The annotation is the documented convention in this module (e.g. `relations_obj: list[Relation]` at line 180 uses 3.10+ subscripting under the same protection). If preferred, use `Optional[int]` from `typing` — pick the one that already matches the file's style; the file already uses PEP 604-style under `__future__` annotations, so `int | None` is consistent.
